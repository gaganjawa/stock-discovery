## Security findings and required deployment configuration

Owner auth is a single shared random key of at least 32 characters. HMAC-signed sessions expire after eight hours; cookies are HttpOnly, SameSite=Strict, path `/`, Secure by default. Cookie mutations require an exact Origin; bearer credentials bypass this check by design. Invalid/tampered/expired sessions and key rotation are tested. Logout deletes the browser cookie; it does not revoke a copied signed cookie before expiry. Rotate AUTH_TOKEN and restart API to invalidate all sessions; no per-session revocation or multi-user isolation exists.

Protected research routes include dashboard, initialize, datasets, analysis/read/reveal, scan, replay jobs, scorecard, experiments and export. Public routes include login, static UI, health, fictional demo and FastAPI docs/OpenAPI. A host-level private access boundary must cover the entire site if all content must be private. Direct API ingress must not bypass that boundary.

Production requirements (currently a manual deployment gate, **not enforced by an environment validator**):

- Use HTTPS termination with a valid certificate; set `APP_ORIGIN` to the exact HTTPS origin and `COOKIE_SECURE=true`. Current Nginx listens on HTTP; the app does not refuse insecure origins or `COOKIE_SECURE=false`. That override is allowed only on loopback preview. Test actual TLS, cookie delivery, origin rejection and login through the chosen proxy before deployment.
- Generate separate strong owner/database secrets, store server-side with restricted permissions, and rotate the local database default before hosting. Never include credentials in URLs, logs, screenshots, command history or client bundles. Changing POSTGRES_PASSWORD in `.env` alone does not rotate an initialized database password; rotate the database role and service configuration together.
- Separate migration owner from a least-privilege API/worker database role and verify required grants. Current `stock_discovery` role is a superuser and can bypass immutability protections. Compose does not currently expose separate role settings.
- Ports 5432/8000/5173 bind to loopback; no host-network or privileged mode. All services share a normal Compose bridge with outbound access, not an egress-isolated network. On the chosen host remove unnecessary published database/API ports, restrict host/firewall access and isolate the database from the web tier. Keep provider credentials absent.
- API/worker run as 10001. Nginx retains a root master with unprivileged workers; review host/runtime restrictions, filesystem/capability policy and dependency/image advisories before hosting. This is not a penetration test or complete vulnerability audit.
- Worker emits IDs/status/error class rather than exception details; API maps database errors to a generic response. Access logs can contain request paths/query strings, and there is no general redaction filter. Apply proxy/app log sanitization and retention, disallow secrets in request URLs, and test canary redaction. Add login throttling and operational health/queue alerts before exposure.

## Backup and recovery procedure

Existing `scripts/backup_restore.py` creates a PostgreSQL custom-format dump with exclusive creation and mode 0600. It refuses overwrite, checks source stability, optionally restores with a single transaction into `stk_restore_<random>`, compares all research-table row hashes, and drops only that generated restore database in a finally block.

For a local verification backup, from the repository with the configured database running:

```sh
docker-compose stop api worker
# Choose a new path each time; keep the database running.
.venv/bin/python scripts/backup_restore.py backups/pre-release.dump --verify-restore
# Restart even if verification failed; investigate a failed dump before using it.
docker-compose start api worker
.venv/bin/python scripts/smoke_compose.py
```

Do not run backup during writes. Failure after file creation may leave an unusable dump; do not treat file existence as success. Large dumps/fingerprints are buffered in memory. Hash comparison covers research rows, not roles, grants, non-research data, sequence state or deployed configuration; successful pg_restore provides schema restoration evidence but not full host recovery. Dumps exclude PostgreSQL global roles and `.env`, certificates, image artifacts and external configuration. No point-in-time recovery/WAL archive exists. Current Compose relies on an anonymous database volume: preserve its identity; do not use `down --volumes`, volume pruning or assume a newly created container reattaches the correct data volume. Establish an explicit persistent-volume/retention policy before hosting.

Before deployment, select (without purchasing in this task) an encrypted off-host destination, separate key custody, backup cadence/retention, failure alerts and owner-approved RPO/RTO. Record checksum, UTC time, code/image identifiers, schema revision and restore outcome. Keep configuration recovery material separately encrypted. Test recovery from the encrypted off-host copy; a same-host disposable restore is insufficient disaster-recovery evidence. No measured production RPO/RTO is claimed.

For recovery, stop writers, preserve the failed database/volume and logs, provision an empty recovery database with appropriate roles, decrypt the selected verified dump securely, restore using `pg_restore --single-transaction --exit-on-error`, and compare its research-table fingerprints and schema revision against the recorded backup. Point an isolated copy of the matching application revision at it, run smoke/auth/replay checks, then deliberately switch the service database configuration. Restart exactly one worker only after acceptance. Never restore over the only surviving database copy. Infrastructure/configuration switch and encrypted recovery remain to be rehearsed on the selected private host.

## Rollback

The migration tests prove SQL lifecycle behavior, not data-preserving downgrade: 0004→0003 drops jobs; 0003→0002 drops dataset manifests/checkpoints; 0002→0001 removes immutability protections; downgrade to base deletes research data. Do not use downgrade-to-base as a production rollback command.

`17e4300` is the nearest earlier tested same-schema diagnostic fallback: migration/shared/frontend files are identical to `067860f`, but it loses the Unicode auth fix, non-root Python runtimes and worker version configuration. It is **not an approved hosted security fallback**. `002ddf0` has the Replay defect and failed CI. No prior fully accepted private-deployment rollback image exists.

Before deployment retain immutable images/configuration for the candidate and an approved secure fallback. Rehearse on a disposable clone:

1. Stop API/worker writes; take and verify a pre-change backup. Record code version, images, schema and volume identity.
2. For a same-schema rollback, restore the approved previous application images/configuration without running a schema downgrade; set CODE_VERSION to that revision. Do not reset this working tree or touch unrelated files.
3. For incompatible schema changes, restore the matching pre-change backup into a separate database and switch configuration after verification. Document loss of writes since the backup; preserve the newer database for investigation.
4. Verify migration revision, login/authorization, UI assets, freeze/reveal, scorecard and one queued job. Re-enable exactly one worker and confirm health. Keep the failed revision isolated for diagnosis.
