# STK-016 — Secure private deployment preparation

12 October 2026. **Backlog + Blocked / PARTIAL**, not deployed. Approved platform: STK-008 Hetzner CX23, Linux AMD64, Docker Compose; restic/B2 backup. Purchases and external deployment require explicit owner authorization after region, final pricing and backup-key custody confirmation.

## Implemented and locally verified

Standalone `deploy/compose.private.yaml` avoids merging permissive preview defaults. Explicit external named database volume (never implicitly create/replace existing data), separate owner/migration and `stk_runtime` credentials, file-mounted secrets, no published database/API ports. API/worker use internal networks; web joins a separate ingress network and publishes only 127.0.0.1:5173. Web cannot join the database network. Apply host outbound restrictions to the ingress network before hosting.

API/worker UID 10001 and web UID 101; read-only application filesystems, bounded tmpfs, dropped capabilities, no-new-privileges, process/memory/log limits, restart policies and health checks. PostgreSQL keeps its upstream initialization privilege model; no privileged containers or Docker socket mounts. Operational host tasks necessarily have Docker-admin access, kept outside runtime containers.

Private startup rejects insecure/non-tailnet origins, insecure cookies, absent secret files, privileged runtime username, weak database password and missing code provenance. Owner secret file requires at least 32 characters. Eight-hour signed owner sessions and exact mutation Origin checks remain. Single-process login throttle: five attempts per peer per minute, twenty globally; ignores forwarded headers. Behind Nginx this intentionally throttles the single owner's shared proxy peer. Bounded lockout resets after sixty seconds; do not run multiple API processes without a shared limiter.

Role bootstrap runs explicitly after migration. Runtime gets schema USAGE, SELECT/INSERT, UPDATE on jobs and sequence USAGE. No schema ownership, database creation, role creation, superuser, bypass RLS, table DDL, DELETE or TRUNCATE grants. New tables require re-running explicit bootstrap after migration. No migration history changed.

Proxy logs contain status/duration only; request URLs, headers and bodies excluded. Proxy diagnostic error log disabled to prevent raw request leakage. API access logging disabled. Runtime-role and migration tests run only in the explicitly disposable stk013_test database; migration verifier now removes inherited DATABASE_URL_FILE before setting the disposable URL.

## Deployment procedure and remaining gates

1. Confirm region, final checkout price, backup-key custody, tailnet/provider-account MFA and deployment authorization. Capture target host/software licence inventory (STK-009).
2. Build and retain immutable tested API/worker/web images. Set API_IMAGE, WORKER_IMAGE and WEB_IMAGE to exact image IDs/digests; CODE_VERSION to tested commit. No mutable latest tags for release.
3. Prepare a root-only secret directory outside the repository. Supply owner_password, owner_database_url, runtime_password, runtime_database_url, owner_access_key. Generate distinct random values of at least 32 characters. Database URLs address `database/stock_discovery`, using `stk_owner` or `stk_runtime` as appropriate. Ensure container UID 10001 can read only its mounted files; Compose file secrets do not remap ownership. The host directory must remain inaccessible to other users. Do not print resolved Compose secrets.
4. Set SECRETS_DIR, DATABASE_VOLUME, APP_ORIGIN=https://<neutral-host>.<tailnet>.ts.net and image variables in a protected environment. For a new host explicitly create its named volume; for existing preview data preserve and restore into a new volume after verified backup. Never attach an empty volume in place of existing data or use down --volumes.
5. After authorization: `docker compose -f deploy/compose.private.yaml up -d`. Configure Tailscale Serve HTTPS to loopback port 5173, with owner-device-only tailnet ACLs, no Funnel. Default-deny public ingress including SSH, HTTP, HTTPS and database on IPv4/IPv6; use tailnet key-only SSH and retain console recovery. Validate effective Docker/firewall rules.
6. Test real certificate, secure cookie delivery, unauthorized/Origin/throttle rejection, entire-site privacy, reboot, encrypted B2 restore and approved-image rollback. Record evidence in STK-018. This task has not performed any external step.
