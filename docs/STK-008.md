## 5. Backup and recovery plan — proposed, not configured

Reuse `scripts/backup_restore.py` as documented in STK-018: custom-format PostgreSQL dump, exclusive 0600 output, source-stability check and optional disposable restore with research-table fingerprint comparison. It does not encrypt, capture roles/configuration, provide PITR, or prove complete disaster recovery. A dump file's existence is not success.

- **Cadence:** nightly after the daily worker run, plus before schema/image/configuration changes. Stop API/worker writers while keeping PostgreSQL running; run the existing script with `--verify-restore` and a unique path. A future timer wrapper must restart services on both success and failure, serialize executions and alert on any failed dump/restore/upload. Resume writers after local verification, then encrypt/upload the stable dump.
- **Off-host:** restic encrypted repository through the recommended S3-compatible API in a private Backblaze B2 bucket in a separately selected region/account [S4,S11]. Store only encrypted repository objects; use TLS, bucket-scoped credentials, account MFA and a dedicated backup identity. Retain a second encrypted recovery copy on owner-controlled offline media if available; cost of new media is UNVERIFIED. Do not configure a bucket in this task.
- **Retention:** 7 daily, 4 weekly and 3 monthly recovery points; keep at most two recent verified local dumps. Up to 14 distinct full dumps × assumed 5 GB = 70 GB, with 30 GB allowance for configuration, repository overhead and churn = 100 GB planning storage. Do not assume effective deduplication of compressed dumps. Expired B2 versions and abandoned uploads must be included in usage and safe cleanup; do not apply blind bucket expiration that corrupts the restic repository. Pre-change points count against capacity and must be reconciled after acceptance.
- **Deletion resistance:** a root compromise can steal online restic credentials/password. Encryption alone does not prevent deletion. Keep pruning credentials off the VPS and validate restricted uploader permissions against restic operations; retain the offline copy until an immutable/append-only design is proven. Do not claim B2 Object Lock is configured or automatically compatible with pruning.
- **Files/configuration:** separately encrypt `.env`, Compose deployment override, firewall/private-access configuration, timer scripts, grants/roles (e.g. an encrypted `pg_dumpall --globals-only` export), image digests, matching source revision, migration revision and permitted irreplaceable imported files. Include private TLS recovery configuration where needed, or document re-issuance. Do not back up live PGDATA as a replacement for a consistent dump. No additional persistent app file mounts are declared by current Compose; inventory future imports/exports before enabling them. Respect market-data archival rights. Git alone does not preserve ignored configuration, data or guaranteed image availability.
- **Keys:** random restic repository password in an owner password manager plus an offline recovery copy separate from VPS/B2. Restricted root-readable 0600 runtime password file is needed for unattended backup; never put it in Git, logs or command arguments. Keep account recovery codes separately. Record repository identifier/region/key recovery procedure without secrets. Credential rotation does not make already stolen decryption material safe; create a new repository/key if compromised.
- **Evidence/alerts:** record UTC timestamp, checksum, schema/code/image identifiers, size, table fingerprints, local restore outcome and uploaded snapshot ID. Alert on no successful off-host backup within 26 hours, failed checks, growing queue, low disk or approaching quota. Use an external dead-man check/owner notification channel to detect host outage; destination and any monitoring subscription remain owner decisions, with no paid service assumed.

**Storage cost:** B2 verified $6.95/TB/month, free transactions and free egress up to 3× average stored data [S4]. At 100 decimal GB, `$0.695 × 95 × 1.18 × 1.03 = ₹80.25/month`. No free-storage concession is deducted. ₹150 allowance covers about 187 GB storage at this factor, before chargeable egress. Initial full restore should fit the included egress if average stored volume is sufficient; early-month/repeated restores may not. Excess egress price is UNVERIFIED here; confirm it before recovery testing and use reserve if needed.

**Objectives:** RPO ≤24 hours from the newest completed off-host backup; target RTO ≤8 hours after the owner begins recovery, assuming account access, keys, image availability and replacement capacity. Owner response delay adds to outage. These are objectives, not measured guarantees; no WAL/PITR or automatic failover is proposed.

**Restore procedure:**

1. Stop writers, preserve the failed volume and evidence, and select a completed off-host snapshot. Provision a separate isolated Linux host/database; never overwrite the sole surviving copy.
2. Recover restic credentials/password from independent custody; download, decrypt and check the snapshot/checksum. Use matching PostgreSQL major version, recorded application images and schema.
3. Recreate/review roles and grants securely, then restore to an empty database with `pg_restore --single-transaction --exit-on-error`. Restore configuration with restricted permissions; rotate potentially compromised credentials.
4. Compare schema and recorded research-table fingerprints; separately check roles/grants, sequences, configuration and any non-research tables/files. Run smoke/authentication and one representative replay/queued job in isolation. Existing row hashes alone do not cover these additional items.
5. Deliberately switch private service configuration, start exactly one worker, verify HTTPS/health and the next backup; retain the failed copy for diagnosis. Rehearse from the encrypted off-host copy before deployment, monthly on an isolated database and after major changes. Record elapsed time and actual data loss; revise RPO/RTO if missed.
